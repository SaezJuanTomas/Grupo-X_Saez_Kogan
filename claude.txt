# Grupo X - Documentación técnica completa del proyecto

Este documento describe el estado actual del repositorio y funciona como referencia técnica para comparar la implementación con la tesis de Ingeniería. La regla principal seguida para redactarlo es la siguiente: todo lo que se afirma surge del código fuente, de la configuración del proyecto, de los tests y de los archivos de automatización incluidos en este repositorio.

Si algún aspecto no puede deducirse con certeza del código, se indica explícitamente.

## 1. Resumen general

El proyecto es una plataforma web de gestión de vulnerabilidades de seguridad informática. El sistema permite registrar, clasificar, asignar, comentar, auditar y visualizar vulnerabilidades asociadas a empresas, con un backend en FastAPI, un frontend en React con TypeScript, persistencia en PostgreSQL y automatización mediante n8n.

El objetivo funcional es centralizar el seguimiento operativo de vulnerabilidades y automatizar el ingreso de hallazgos desde fuentes externas, especialmente NVD y FIRST EPSS, enriqueciendo cada hallazgo con una puntuación de riesgo propia llamada IRC.

El problema que resuelve es doble:

- Reducir la carga manual de análisis y carga de vulnerabilidades.
- Dar trazabilidad operativa entre fuente externa, empresa afectada, tecnología correlacionada, analista asignado, historial y visualización frontend.

El sistema no es un simple CRUD aislado. Tiene una lógica de negocio más amplia:

- Autenticación JWT con refresh token rotation.
- Control de roles en backend y frontend.
- Historial automático de acciones.
- Integración n8n para ingestión de CVEs.
- Correlación de tecnologías/activos a partir de descripciones.
- Cálculo propio del IRC.
- Deduplciación por CVE y empresa.

## 2. Arquitectura completa

### Vista general

La arquitectura real del repositorio es una aplicación monorepo con tres piezas principales:

- Backend: FastAPI + SQLAlchemy + Pydantic.
- Frontend: React + TypeScript + Vite.
- Automatización: n8n, que consume NVD y empuja datos al backend.

PostgreSQL es la base persistida principal. Los tests del backend usan SQLite en memoria.

### Flujo de comunicación

```mermaid
flowchart LR
  A[NVD API] --> B[n8n workflow]
  C[FIRST EPSS API] --> B
  B --> D[FastAPI webhook /webhook/n8n/vulnerabilidades]
  B --> E[FastAPI webhook /webhook/n8n/empresas]
  D --> F[SQLAlchemy / PostgreSQL]
  G[Frontend React] --> H[FastAPI REST API]
  H --> F
  G --> H
```

### Componentes

#### Frontend

El frontend es una SPA en React 18 con Vite. Consume la API del backend mediante Axios. La UI está pensada como un panel de operación para administradores y analistas.

Características visibles en el código:

- Login y sesión local mediante localStorage.
- Navegación con rutas protegidas.
- Vistas para dashboard, vulnerabilidades, empresas, usuarios, equipo y estadísticas.
- Formulario de creación y edición de entidades.
- Gráficos en estadísticas con Recharts.

#### Backend

El backend usa FastAPI como capa HTTP. La aplicación se organiza en patrones de router, service y repository:

- Router: expone endpoints HTTP.
- Service: contiene lógica de negocio.
- Repository: encapsula acceso a SQLAlchemy/ORM.

Además incluye módulos core para:

- configuración,
- autenticación/autorización,
- logging,
- rate limiting,
- manejo global de excepciones.

#### PostgreSQL

El archivo `docker-compose.yml` define PostgreSQL como base de datos del entorno local. El backend apunta por defecto a `postgresql://postgres:postgres@localhost:5435/grupo_x`.

#### n8n

n8n actúa como motor de automatización. Su workflow importa CVEs desde NVD, calcula y normaliza métricas, correlaciona tecnologías, calcula IRC, verifica duplicados y finalmente inserta las vulnerabilidades en el backend.

#### NVD y FIRST EPSS

El workflow consulta:

- NVD para obtener vulnerabilidades públicas.
- FIRST EPSS para obtener el valor EPSS cuando está disponible.

Si EPSS no puede recuperarse, el workflow aplica una estimación interna basada en CVSS.

## 4. Backend

### 4.1 Arquitectura

El backend está organizado en capas:

1. Router: recibe la petición HTTP.
2. Dependencias: resuelven sesión, usuario actual y permisos.
3. Service: aplica reglas de negocio.
4. Repository: ejecuta consultas ORM.
5. Modelos: representan las tablas.

El entrypoint está en `backend/app/main.py`. Ahí se crea la app FastAPI con título, versión, `docs_url` y `redoc_url`, se registran middleware, handlers globales y routers.

### 4.2 Flujo de una petición

Una petición típica pasa por:

- `SlowAPIMiddleware` para rate limiting.
- `LoggingMiddleware` para request ID y tiempo de respuesta.
- `CORSMiddleware` con orígenes definidos en config.
- Handlers de excepción globales.
- Router.
- Service.
- Repository.
- SQLAlchemy.
- Base de datos.

### 4.4 Services

#### `auth_service.py`

Contenido relevante:

- verifica credenciales de login,
- valida password con bcrypt,
- crea usuarios con hash,
- retorna el usuario autenticado.

#### `company_service.py`

Responsabilidad:

- lista empresas,
- obtiene una empresa,
- crea empresas,
- actualiza empresas,
- desactiva y reactiva empresas.

Lógica importante:

- Si la empresa se crea sin `assigned_analyst_id`, busca el primer analista disponible.
- Después de crear una empresa intenta disparar un webhook hacia n8n con `N8N_WEBHOOK_URL`.
- La desactivación es lógica, no borrado físico.

#### `user_service.py`

Responsabilidad:

- listar usuarios con cantidad de vulnerabilidades asignadas,
- crear usuarios evitando duplicados,
- actualizar usuarios,
- recalcular el conteo de asignaciones.

#### `vulnerability_service.py`

Responsabilidad:

- listar vulnerabilidades con filtros,
- obtener por ID,
- crear con deduplicación por CVE y empresa,
- actualizar campos,
- eliminar,
- agregar comentarios.

Lógica importante:

- Al crear una vulnerabilidad, si ya existe la misma combinación `cve + company_id`, devuelve error de duplicado.
- Al crear una vulnerabilidad, inserta un `HistoryLog` con acción `Creado`.
- Al cambiar asignación o estado, genera entradas de historial automáticamente.
- Al agregar comentario, también crea historial con acción `Comentario agregado`.

#### `statistics_service.py`

Responsabilidad:

- conteos por severidad,
- conteos por estado,
- usuarios activos,
- actividad de analistas,
- distribución de IRC en rangos.

### 4.7 Autenticación

#### `auth.py`

Responsabilidades:

- `hash_password`
- `verify_password`
- `create_access_token`
- `create_refresh_token`
- `refresh_access_token`
- `revoke_all_user_tokens`

Detalles:

- El access token incluye `sub`, `role`, `type=access`, `ver` y `exp`.
- El refresh token incluye `sub`, `jti`, `type=refresh` y `exp`.
- Los refresh tokens se guardan en la tabla `refresh_tokens`.
- Al refrescar se revoca el token anterior y se emite uno nuevo.
- Al cerrar sesión se revocan los refresh tokens del usuario y se incrementa `token_version`.

### 4.8 Seed

`seed.py` crea datos iniciales si la base está vacía:

- 4 usuarios,
- 5 empresas,
- 6 vulnerabilidades,
- comentarios,
- historial.

El seed es muy importante porque los tests dependen de él y porque el frontend muestra datos coherentes al iniciar.

## 6. API

### Conteo exacto de endpoints

El backend expone 27 endpoints HTTP en total si se incluye `/health`:

- 4 de autenticación
- 5 de vulnerabilidades
- 6 de empresas
- 3 de usuarios
- 2 de comentarios
- 1 de historial
- 2 de estadísticas
- 3 de n8n
- 1 de health

Si se cuentan solo los routers funcionales montados explícitamente, el total es 26 endpoints.

### 6.1 Autenticación

#### `POST /auth/login`

- Autenticación: no requiere token.
- Body: `username`, `password`.
- Respuesta: `access_token`, `refresh_token`, `token_type`, `user_id`, `username`, `role`.
- Restricción adicional: rate limit por SlowAPI.

#### `POST /auth/refresh`

- Autenticación: refresh token en body.
- Body: `refresh_token`.
- Respuesta: nuevo `access_token` y nuevo `refresh_token`.

#### `POST /auth/logout`

- Autenticación: Bearer token.
- Efecto: revoca refresh tokens del usuario y aumenta `token_version`.

#### `GET /auth/me`

- Autenticación: Bearer token.
- Respuesta: `id`, `username`, `email`, `role`, `active`.

### 6.2 Vulnerabilidades

#### `GET /vulnerabilidades`

- Autenticación: Bearer token.
- Query params: `role`, `user_id`, `page`, `page_size`.
- Comportamiento: si `role=analyst` y `user_id` está presente, filtra por analista asignado.
- Respuesta: lista de vulnerabilidades con empresa y analista embebidos.

#### `GET /vulnerabilidades/{id}`

- Autenticación: Bearer token.
- Respuesta: una vulnerabilidad o 404.

#### `POST /vulnerabilidades`

- Autenticación: admin.
- Body: `VulnerabilityCreate`.
- Respuesta: vulnerabilidad creada.
- Lógica: deduplicación `cve + company_id`.

#### `PATCH /vulnerabilidades/{id}`

Las variables conocidas están definidas en `backend/app/core/config.py` y reflejadas en `.env.example`.

### Obligatorias para funcionamiento real

- `DATABASE_URL`: cadena de conexión a PostgreSQL.
- `SECRET_KEY`: clave usada para JWT.
- `N8N_API_KEY`: clave que el backend espera en el header `x-api-key`.
- `N8N_WEBHOOK_URL`: URL que el backend llama al crear empresas.

### Configurables

- `ALGORITHM`: algoritmo JWT, por defecto `HS256`.
- `ACCESS_TOKEN_EXPIRE_MINUTES`: duración del access token.
- `REFRESH_TOKEN_EXPIRE_DAYS`: duración del refresh token.
- `CORS_ORIGINS`: orígenes permitidos.
- `RATE_LIMIT_LOGIN`: límite de login configurado en texto, aunque la ruta de login usa actualmente un valor hardcodeado.
- `NVD_API_KEY`: opcional para aumentar rate limits en NVD.
- `LOG_LEVEL`: nivel de logging.

### Observación importante

El workflow de n8n incluye una clave hardcodeada `grp-x-n8n-secret-2025` en el JSON importable. El backend, en cambio, usa el valor de `N8N_API_KEY`. Para que la integración funcione sin editar el workflow, ambos valores deben coincidir.

También existe una discrepancia entre configuración y uso real del rate limit de login:

- `RATE_LIMIT_LOGIN` en config está seteado como `5/15minutes`.
- El decorador de ruta en `/auth/login` usa `5/minute`.

La documentación oficial del comportamiento debe considerar el valor efectivo del código, no solo el valor configurado.

## 10. Workflow de n8n

### 10.1 Objetivo

Automatizar la ingestión de vulnerabilidades desde NVD, enriqueciendo cada registro con EPSS, correlación de activos, IRC, asignación de analista y deduplicación antes de insertarlo en FastAPI.

### 10.2 Triggers

El workflow se activa de tres formas:

- `Manual Trigger`
- `Schedule Trigger` cada 3 horas
- `Webhook Trigger` desde el backend

### 10.3 Nodo por nodo

#### 1. Manual Trigger

- Propósito: ejecución manual.
- Entrada: ninguna.
- Salida: dispara el flujo hacia NVD.
- Dependencias: ninguna.

#### 2. Schedule Trigger

- Propósito: ejecución periódica cada 3 horas.
- Entrada: tiempo.
- Salida: dispara el flujo hacia NVD.
- Dependencias: ninguna.

#### 3. Webhook Trigger

- Propósito: ejecución iniciada por el backend cuando se crea una empresa.
- Entrada: POST al path `trigger-nvd-fetch`.
- Salida: dispara el flujo hacia NVD.
- Dependencias: backend y `N8N_WEBHOOK_URL`.

#### 4. Fetch NVD API

- Propósito: consultar CVEs en NVD.
- Entrada: no recibe datos previos.
- Salida: JSON con vulnerabilidades.
- Transformación: realiza GET sobre `https://services.nvd.nist.gov/rest/json/cves/2.0`.
- Parámetros visibles: `resultsPerPage=20` y keywords como nginx, apache, wordpress, tomcat, kubernetes, docker, linux, windows, .net, mysql, postgresql, sql server y redis.
- Dependencias: red externa y, opcionalmente, `NVD_API_KEY` si se ajusta el request manualmente.

#### 5. Extract Fields

- Propósito: extraer campos útiles del JSON de NVD.
- Entrada: respuesta NVD.
- Salida: objetos con `cve`, `cvss`, `description`, `publishedDate`, `timestamp`.
- Transformación: elige la primera métrica disponible entre CVSS v3.1, v3.0 y v2; recorta descripciones a 500 caracteres.
- Dependencias: estructura del JSON de NVD.

#### 6. Filter Completeness

- Propósito: filtrar elementos sin descripción útil.
- Entrada: items extraídos.
- Salida: items con descripción no vacía.
- Transformación: evalúa la longitud de `description`.

#### 7. Normalize Data

- Propósito: normalizar CVSS y obtener EPSS.
- Entrada: item con CVE y CVSS.
- Salida: item normalizado con `cvss`, `epss`, `epss_source`, `description`, `publishedDate`, `normalized_timestamp`.
- Transformación:
  - limita CVSS al rango 0-10,
  - consulta FIRST EPSS por CVE,
  - si no hay respuesta, estima EPSS internamente según CVSS con una distribución heurística,
  - recorta espacios de la descripción.
- Dependencias: FIRST EPSS API y red.

#### 8. Asset Correlation

- Propósito: identificar el activo/tecnología más probable afectado.
- Entrada: descripción normalizada.
- Salida: `correlated_asset` y `asset_criticality`.
- Transformación: búsqueda por palabras clave con estructura `if / else if`.
- Dependencias: texto descriptivo del CVE.

#### 9. Calculate IRC

- Propósito: calcular el Índice de Riesgo Completo.
- Entrada: `cvss`, `epss`, `asset_criticality`.
- Salida: `irc` truncado a dos decimales.
- Fórmula:

```text
IRC = (CVSS * 0.4) + (EPSS * 10 * 0.4) + (Asset Criticality * 0.2)
```

#### 10. Detect Critical

- Propósito: bifurcar el flujo según el IRC.
- Entrada: item con IRC calculado.
- Salida: rama crítica o normal.
- Regla: crítico si `irc >= 7.5`.

#### 11. Critical Path - Mark

- Propósito: etiquetar el caso como crítico.
- Entrada: item crítico.
- Salida: item con `is_critical=true`, `severity_override='Crítica'`, `alert_event='CRITICAL_ALERT_GENERATED'`.
- Dependencias: rama crítica.

#### 12. Normal Path - Mark

- Propósito: asignar severidad en el camino no crítico.
- Entrada: item no crítico.
- Salida: item con `is_critical=false`, `severity_override` calculada y `alert_event=null`.
- Dependencias: rama normal.

#### 13. Merge Branches

- Propósito: unir ambas ramas.
- Entrada: salida crítica o normal.
- Salida: flujo único hacia asignación.

#### 14. Assign Analyst

- Propósito: correlacionar la vulnerabilidad con una empresa y decidir analista.
- Entrada: item con descripción, activo correlacionado, severidad y IRC.
- Salida: payload listo para insertar.
- Transformación:
  - consulta `/webhook/n8n/empresas` con API key,
  - compara tecnologías de cada empresa contra descripción y activo,
  - puntúa coincidencias,
  - elige compañías con score > 0,
  - si no hay coincidencias, usa la primera compañía disponible,
  - asigna analista `2` para severidad `Crítica` o `Alta`, `3` para `Media` o `Baja`,
  - construye el payload con `cve`, `description`, `affected_technology`, `irc`, `severity`, `status='Pendiente'`, `company_id`, `assigned_analyst_id`.
- Dependencias: backend webhook de empresas y API key.

#### 15. Idempotency Check

- Propósito: evitar duplicar vulnerabilidades.
- Entrada: payload propuesto.
- Salida: resultado de existencia.
- Transformación: consulta `/webhook/n8n/vulnerabilidades/existe?cve=...&company_id=...`.
- Dependencias: backend webhook, API key y deduplicación en el servicio.

#### 16. Skip if Exists

- Propósito: decidir si se crea o se omite.
- Entrada: resultado de existencia.
- Salida: rama de creación o rama vacía.
- Regla: solo continúa si `exists == false`.

#### 17. POST to FastAPI

- Propósito: crear la vulnerabilidad en el backend.
- Entrada: payload final.
- Salida: respuesta del backend.
- Transformación: POST a `/webhook/n8n/vulnerabilidades` con JSON body y API key.
- Dependencias: backend funcionando y API key válida.

#### 18. Generate Summary

- Propósito: consolidar resultados del workflow.
- Entrada: resultados previos.
- Salida: resumen con `created`, `skipped_duplicates`, `errors`, `status`, `timestamp`.
- Dependencias: resultados del flujo.

### 10.4 Flujo completo de la vulnerabilidad

1. n8n consulta NVD.
2. Extrae CVE, CVSS y descripción.
3. Filtra registros incompletos.
4. Normaliza CVSS.
5. Consulta FIRST EPSS; si falla, estima EPSS.
6. Correlaciona tecnologías por palabras clave.
7. Calcula IRC.
8. Clasifica criticidad.
9. Asigna empresa y analista.
10. Verifica duplicado por `cve + company_id`.
11. Inserta en FastAPI si no existe.
12. FastAPI persiste la vulnerabilidad en PostgreSQL.
13. El backend expone la nueva información a la API REST.
14. El frontend la consume y la presenta en las vistas.

## 11. Integración con NVD

### Endpoint utilizado

El workflow usa:

`https://services.nvd.nist.gov/rest/json/cves/2.0`

### Método y parámetros

- Método: GET.
- Parámetro visible: `resultsPerPage=20`.
- Query de keywords: lista de tecnologías y plataformas comunes.

### Frecuencia

- Ejecución manual.
- Cada 3 horas por scheduler.
- Ejecución disparada por webhook desde backend al crear empresas.

### Procesamiento de resultados

- Se toma el primer valor disponible de CVSS v3.1, v3.0 o v2.
- Se limita el texto descriptivo a 500 caracteres.
- Se descartan registros sin descripción.
- Se conserva la fecha de publicación cuando existe.

## 12. Integración con FIRST EPSS

### Endpoint

El workflow consulta:

`https://api.first.org/data/v1/epss?cve=...`

### Fuente real usada en el proyecto

La fuente real de EPSS usada por el workflow es FIRST.org, mediante la API pública `https://api.first.org/data/v1/epss`. En el nodo de normalización, el valor se solicita por CVE y se usa como fuente primaria. Si la consulta falla o no devuelve datos, el workflow aplica un fallback interno etiquetado como `cvss-estimate`.

### Utilización

- Se usa para enriquecer el cálculo del IRC.
- El valor recuperado se transforma a la escala interna 0-10 multiplicando por 10 dentro de la fórmula del IRC.

### Fallback

Si FIRST EPSS falla o no devuelve datos:

- se aplica una heurística interna basada en el CVSS,
- se elige un rango aleatorio acotado según severidad,
- se registra `epss_source = cvss-estimate`.

### Procesamiento

- El valor se redondea a 4 decimales.
- El resultado final se usa solo para el IRC y para la clasificación interna.

## 15. Decisiones de diseño

### Separación por capas en backend

La división router/service/repository permite aislar HTTP, negocio y persistencia. Esto simplifica el testeo y reduce el acoplamiento.

### JWT con token_version

Se eligió un esquema con `token_version` para invalidar access tokens luego del logout. Esto evita depender solo de la expiración temporal.

### Refresh token rotation

Cada refresh invalida el token anterior, lo que mejora seguridad frente a reuso de tokens.

### Historial de auditoría

Toda acción importante crea rastros en `history_logs`, lo que es útil para trazabilidad operacional y para una tesis orientada a gobierno o seguridad.

### Cálculo IRC propio

El sistema no adopta solo CVSS. Combina CVSS, EPSS y criticidad del activo para priorizar por contexto de negocio.

### Correlación por palabras clave

La correlación de activos en n8n se implementa como heurística por keywords. Es una solución simple, transparente y fácil de defender en una tesis, aunque no es semánticamente robusta.

### Frontend centrado en rol

La UI no intenta ser genérica para todos los perfiles. Admin y analyst tienen vistas diferentes y esa diferencia se refleja en navegación, acceso a páginas y acciones permitidas.

## 16. Limitaciones conocidas

No se ocultan aquí las limitaciones que se desprenden del código actual:

- No se encontró un directorio de migraciones Alembic.
- La integración n8n usa una clave hardcodeada en el workflow JSON; debe coincidir con la del backend.
- La configuración `RATE_LIMIT_LOGIN` existe, pero el decorador de login usa un valor hardcodeado distinto.
- El frontend no modela el rol `viewer` aunque el backend sí lo define.
- El frontend guarda solo una sesión simplificada en localStorage; no persiste email ni permisos detallados.
- `App.tsx` carga comments/history globalmente para el primer item disponible, no para el detalle activo de forma centralizada.
- El workflow de n8n depende de `host.docker.internal`, lo que es apropiado en entornos locales pero no universal para despliegues distintos.
- `docker-compose.yml` referencia `n8n_workflow_seed.json`, pero ese archivo no está en el repositorio actual.
- La heurística de EPSS fallback introduce aleatoriedad cuando FIRST EPSS no responde.

## 17. Mejoras futuras

Estas mejoras no cambian el funcionamiento actual, pero serían extensiones naturales:

- Añadir migraciones Alembic formales.
- Exponer el rol `viewer` también en el frontend.
- Unificar el valor de rate limit entre config y decorador.
- Externalizar la API key de n8n fuera del workflow JSON.
- Reemplazar la correlación por keywords con una lógica semántica más avanzada.
- Guardar trazas más ricas de actividad del usuario en frontend y backend.
- Incorporar tests del workflow n8n o validación automatizada del JSON importado.
- Mejorar el detalle del dashboard con filtros temporales configurables en frontend.
- Introducir paginación real en el frontend para listados muy grandes.
- Separar el cache de sesión local de los tokens para hacer la autenticación más explícita.

## 18. Resumen final

El proyecto implementa una plataforma de gestión de vulnerabilidades con tres niveles de funcionamiento coordinado.

Primero, el backend FastAPI expone la API principal y las rutas de integración. Allí se resuelven autenticación JWT, autorización por roles, CRUD de usuarios, empresas y vulnerabilidades, comentarios, historial y estadísticas. La persistencia se apoya en SQLAlchemy y PostgreSQL, con un esquema de tablas centrado en empresas, usuarios, vulnerabilidades, comentarios, historial y refresh tokens. El backend agrega además logging, rate limiting, handlers globales y startup con seed.

Segundo, el frontend React consume esa API y presenta la información en una interfaz operativa. La sesión se administra con localStorage y refresh automático. La navegación cambia según el rol, y las pantallas principales permiten visualizar dashboards, administrar empresas y usuarios, explorar vulnerabilidades y revisar detalle, comentarios e historial.

Tercero, n8n actúa como capa de automatización e ingestión. El workflow consulta NVD, extrae campos útiles, calcula o estima EPSS, correlaciona tecnologías, calcula IRC, clasifica criticidad, asigna empresa y analista, evita duplicados por CVE y empresa, y persiste el resultado en el backend.

El sistema está diseñado para que una vulnerabilidad pueda entrar desde NVD, pasar por enriquecimiento automático, quedar almacenada en la base, auditarse en historial y luego visualizarse y gestionarse desde el frontend. Esa cadena completa es el núcleo funcional del proyecto.

En términos de alineación con una tesis de Ingeniería, la implementación actual sí contiene los elementos estructurales necesarios para demostrar automatización, priorización de riesgo, trazabilidad, integración con fuentes externas y una interfaz de operación. Las limitaciones anotadas arriba son reales y deben tenerse en cuenta al comparar el documento académico con el estado exacto del código.
